# Задания (Assignments) — дизайн

**Дата:** 2026-08-04
**Статус:** утверждён, готов к планированию
**Область:** `apps/backend`, `apps/mini-app`, `packages/shared`, `deploy/hermes/skills`

---

## Задача

Владелец занимается с репетитором, но между занятиями не касается материала — стагнация уже пару месяцев. Ежедневная очередь FSRS не помогает: безликий счётчик «12 к повторению» не создаёт повода открыть приложение, а накопленный долг демотивирует.

Решение: агент Hermes после занятия собирает **задание** — ограниченный набор карточек со сроком сдачи. Задание становится главным экраном приложения и главным поводом его открыть. Свободная практика (текущий режим) остаётся как клапан «захотелось погонять».

Задание закрывает три работы одновременно:

- фокус на провалах — агент видит просевшее и собирает интенсив;
- подготовка к следующему занятию — задание привязано к теме;
- внешняя дисциплина — «репетитор задал» работает там, где «12 due» не работает.

Побочная, но существенная ценность: выполненное задание — артефакт, который можно открыть на следующем занятии. Это замыкает петлю репетитор → агент → ученик → репетитор.

---

## Принципы

**Бэкенд владеет структурой, агент владеет педагогикой.** Бэкенд валидирует форму задания, гарантирует единственность и считает выполнение. Он не решает, какие карточки положить внутрь. Правила подбора живут в markdown-скиле Hermes и правятся без деплоя — как уже устроен `oxenfurt_ingest.md`.

**Одно состояние FSRS.** Задание — это ссылка на существующие карточки плюс срок. Не копия, не отдельная колода. Повторил карточку в задании — расписание сдвинулось, в свободном режиме она больше не всплывёт как «пора».

**Срок не создаёт долга.** Приложение никогда не накапливает просрочку, не показывает красных бейджей и не напоминает. Невыполненное подхватывает агент в следующем задании.

**Терминология.** Сущность — `assignment`, в UI «Задание». Слово «урок» остаётся за `cards.source` (реальное занятие с репетитором). Смешивать нельзя ни в коде, ни в интерфейсе.

## Модель данных

Две новые таблицы. Существующие не меняются.

```
assignments
  id            uuid pk
  title         text notnull        -- «Условные предложения и лексика 28 июля»
  rationale     text                -- markdown, «почему именно это»; nullable
  status        text notnull        -- active | completed | expired
  source        text                -- необязательная привязка к cards.source
  created_at    timestamptz notnull default now()
  due_at        timestamptz notnull
  completed_at  timestamptz

assignment_items
  assignment_id uuid  notnull  fk assignments on delete cascade
  card_id       uuid  notnull  fk cards       on delete cascade
  group_label   text  notnull            -- «Второй кондиционал»
  group_kind    text  notnull            -- topic | new | weak
  position      int   notnull
  completed_at  timestamptz
  pk (assignment_id, card_id)
```

Индексы: частичный уникальный на `assignments(status)` где `status = 'active'` — единственность активного задания обеспечивается БД, а не кодом; `assignment_items(assignment_id, position)`.

`group_kind` управляет цветом маркера в UI: `weak` — оранжевый («забытое с прошлых уроков»), остальные — indigo. Группировка в интерфейсе идёт по `group_label` в порядке первого появления `position`.

Каскадное удаление по `card_id` означает, что удалённая карточка исчезает из задания. Это допустимо: карточки удаляются вручную и редко, а прогресс считается от текущего состава.

**Архивация карточки внутри активного задания.** Пользователь может заархивировать карточку через `POST /cards/:id/archive`, находясь внутри задания. Строка `assignment_items` при этом сохраняется, но карточка исключается и из очереди сессии, и из знаменателя: `total` и `groups[].total` считают только элементы, чья карточка `status='active'`. Заархивировав последнюю невыполненную карточку, пользователь тем самым завершает задание — это корректно, отказ от карточки есть осознанное решение, а не пропуск.

## Жизненный цикл

```
                 POST /agent/assignments
                          │
                          ▼
                      [active] ──── все items выполнены ───▶ [completed]
                          │
                          ├──── due_at прошёл (лениво) ────▶ [expired]
                          │
                          └──── replace:true у нового ─────▶ [expired]
```

**Создание.** Агент вызывает `POST /agent/assignments` — как правило, сразу после `oxenfurt_ingest`, пока транскрипт занятия ещё в контексте. Если активное задание уже есть, запрос отклоняется с `409 assignment_active`, если только не передан `replace: true`.

**Истечение — ленивое.** Любое чтение (`GET /assignments/active`, `GET /assignments`, `GET /agent/diagnostics`) переводит задания с `due_at < now` и статусом `active` в `expired`. Отдельного планировщика нет.

**Выполнение.** Карточка засчитывается, когда получает оценку **Good (3) или Easy (4)** после `created_at` задания. Когда у всех `assignment_items` проставлен `completed_at`, задание переходит в `completed`. Оценка Again или Hard не засчитывает — «зазубрил» означает взял, а не пролистал.

## API

Все agent-эндпоинты — под тем же `OXENFURT_INGEST_TOKEN`, что и `/ingest/cards`. Пользовательские — под JWT.

### `GET /agent/diagnostics`

Срез состояния знаний. Сейчас такого нет вовсе: `card_reviews` пишется, но наружу не отдаётся, поэтому агент физически не может «видеть проблемы». Это пререквизит всей фичи.

```json
{
  "summary": {
    "active_cards": 412,
    "overdue": 63,
    "due_today": 12,
    "leeches": 9
  },
  "overdue": [
    {
      "card_id": "uuid",
      "type": "vocab",
      "label": "bound to",
      "source": "lesson-2026-07-14",
      "due": "2026-07-28T09:00:00.000Z",
      "days_overdue": 7,
      "lapses": 5,
      "reps": 11,
      "difficulty": 8.4,
      "stability": 1.9,
      "last_review": "2026-07-27T20:11:00.000Z"
    }
  ],
  "leeches":  [ /* тот же формат, lapses >= 4, сортировка по lapses desc */ ],
  "fragile":  [ /* тот же формат, высокий difficulty при низкой stability */ ],
  "recent_sources": [
    { "source": "lesson-2026-07-28", "cards": 22, "latest": "2026-07-28T18:40:00.000Z" }
  ],
  "last_assignment": {
    "id": "uuid",
    "title": "Пассивный залог",
    "status": "expired",
    "due_at": "2026-07-31T21:00:00.000Z",
    "completed": 11,
    "total": 18,
    "unfinished_card_ids": ["uuid", "uuid"]
  }
}
```

`label` — краткая подпись карточки: `term` для vocab, `phrase` для phrase, `question` (обрезанный) для theory. Каждый список ограничен 200 строками; параметр `limit` сужает.

### `POST /agent/assignments`

```json
{
  "title": "Условные предложения и лексика 28 июля",
  "rationale": "На занятии второй кондиционал сыпался...",
  "due_at": "2026-08-06T21:00:00.000Z",
  "source": "lesson-2026-07-28",
  "replace": false,
  "items": [
    { "card_id": "uuid", "group_label": "Второй кондиционал", "group_kind": "topic" },
    { "card_id": "uuid", "group_label": "Слова с урока 28 июля", "group_kind": "new" },
    { "card_id": "uuid", "group_label": "Забытое с прошлых уроков", "group_kind": "weak" }
  ]
}
```

Валидация:

| Правило | Ответ при нарушении |
|---|---|
| `items` — 3..30 элементов | `400 invalid_payload` |
| `title` — 1..120 символов | `400 invalid_payload` |
| `rationale` — 0..2000 символов | `400 invalid_payload` |
| `group_label` — 1..80 символов | `400 invalid_payload` |
| `due_at` в будущем и не дальше 30 дней | `400 invalid_due_at` |
| все `card_id` существуют и `status='active'` | `400 unknown_cards` + список |
| дубли `card_id` внутри задания | `400 duplicate_cards` |
| нет активного задания либо `replace: true` | `409 assignment_active` |

Ответ: `{ "assignment_id": "uuid", "items": 18 }`.

`position` присваивается бэкендом по порядку массива. Список никогда не обрезается молча — превышение потолка это ошибка.

### `GET /assignments/active`

Возвращает активное задание вместе с полными DTO карточек в формате, который уже принимает `PracticeSession` (тот же `toDueDto`), плюс `completed_at` по каждому элементу и агрегаты.

```json
{
  "assignment": {
    "id": "uuid",
    "title": "…",
    "rationale": "…",
    "due_at": "…",
    "created_at": "…",
    "completed": 5,
    "total": 18,
    "groups": [
      { "label": "Второй кондиционал", "kind": "topic", "total": 6, "completed": 2 }
    ]
  },
  "cards": [ { "card": { /* DueDto */ }, "completed_at": null } ]
}
```

Нет активного задания — `{ "assignment": null }`, 200. Фронт в этом случае показывает сегодняшний экран как сейчас.

### `GET /assignments`

История: последние 50, новые первыми, без карточек — `id`, `title`, `status`, `due_at`, `completed_at`, `completed`, `total`. Доступно и по JWT (экран истории), и по ingest-токену (агент смотрит, что было).

### `POST /cards/:id/review` — расширение

Добавляется необязательное поле `drill: boolean` (по умолчанию `false`).

- `drill: false` — как сейчас: FSRS пересчитывается, пишется строка в `card_reviews`. Дополнительно: если карточка входит в активное задание, оценка ≥ Good и `completed_at` ещё пуст — он проставляется; если это был последний невыполненный элемент, задание переходит в `completed`.
- `drill: true` — **не** трогает ни `cards`, ни `card_reviews`. Только проставляет `completed_at` в `assignment_items` при оценке ≥ Good. Ответ содержит `{ "fsrs": null, "drill": true }`.

Всё внутри существующей транзакции `applyReview`.

## Повторы и целостность FSRS

Сейчас `PracticeSession` при in-session replay переотправляет ревью (`PracticeSession.tsx:389-402`), из-за чего каждое повторение карточки в одном заходе пишет ещё одну запись в FSRS с околонулевым интервалом. Для нынешнего режима это шум, для зубрёжки — систематическая порча модели.

Правило: **первый ответ по карточке за календарный день — измерение, все последующие в тот же день — тренировка.** Первый идёт без `drill`, остальные с `drill: true`. Определяет это фронт: карточка отправляется с `drill: true`, если она уже получала ответ в текущей сессии, либо если `fsrs.last_review` из DTO приходится на сегодня по местному времени. Поле `last_review` уже есть в `DueCardDto` — менять формат карточки не нужно.

Бэкенд эту проверку не дублирует: при `drill: false` ревью записывается всегда, даже если `last_review` того же дня. Серверная дедупликация по календарному дню сломала бы штатный сценарий свободного режима «повторил утром, вернулся вечером», где второй заход — честное измерение. Решение остаётся за фронтом.

Следствие: карточку можно закрыть в задании чистой зубрёжкой после провала. Это правильно — FSRS уже получил честный сигнал с первого (неудачного) ответа, а последующие повторы это учёба, а не замер.

**Досрочные повторы.** Карточки задания ревьюятся штатно, даже если по FSRS им ещё рано. FSRS-5 корректно обрабатывает ранние повторы через фактический `elapsed_days`. Отдельного «отложенного расписания» в духе Anki filtered decks не заводим — сложность не оправдана при одном пользователе.

## Интерфейс

### Главный экран (макет C)

Есть активное задание:

- шапка без изменений — приветствие, стрик, ранг, настройки, статус Hermes;
- кольцо прогресса считает задание: `5/18`, подпись «задание»;
- под кольцом — заголовок задания и строка «📓 Hermes · сдать до чт, 6 авг»; тап по заголовку открывает `rationale`;
- состав по группам: метка, количество, маркер (оранжевый для `weak`);
- внизу «Продолжить задание» (основная) и «Свободная практика» (вторичная).

Нет активного задания — экран ровно такой, как сейчас: кольцо считает `dueCount`, работает существующая логика пустых состояний. Блок задания просто отсутствует.

Срок показывается относительно («сдать через 2 дн.», в последний день — «сдать сегодня»), в последний день — оранжевым. Красного нет нигде. *Отклонение от первоначального макета («до чт, 6 авг») принято осознанно: на колонке 340 px относительная форма читается быстрее.* «Последний день» считается по календарю, а не по 24-часовым отрезкам — дедлайн завтра в 09:00, прочитанный сегодня в 22:00, это «через 1 дн.», а не «сегодня».

### Сессия по заданию

Тот же `PracticeSession`, очередь берётся из `/assignments/active` вместо `/cards/due`. Отличия:

- порядок — по `position`, невыполненные первыми;
- уже выполненные элементы в очередь не попадают;
- карточка, получившая Again или Hard, возвращается в очередь того же захода (для заданий это поведение по умолчанию, не опция);
- экран `Summary` после задания показывает «X из Y выполнено» и, при полном закрытии, состояние завершения.

### История заданий

Простой список, доступ из шапки главного экрана: заголовок, статус, «14 из 18», дата сдачи. Тап раскрывает `rationale` и состав. Это тот артефакт, который открывают на следующем занятии.

### Свободный режим

Не меняется вообще: выбор режима практики, `bypass_due`, фильтры по типу, Library, Stats, вопросы к агенту — всё как есть.

## Скилл Hermes

Новый файл `deploy/hermes/skills/oxenfurt_assignments.md`, по образцу существующих:

- **Когда создавать** — сразу после `oxenfurt_ingest`, пока транскрипт в контексте; либо по расписанию, если активного задания нет более двух суток.
- **Как читать диагностику** — что означают `lapses`, `difficulty`, `stability`, `days_overdue`, и почему `fragile` важнее, чем просто `overdue`.
- **Состав** — целевой размер ~20 карточек при разрешённых 30; смесь трёх видов: новое с последнего занятия (`new`), тема, где ученик сыпался (`topic`), забытое с прошлых занятий (`weak`). Невыполненное из предыдущего задания (`last_assignment.unfinished_card_ids`) включается в первую очередь.
- **Срок** — по умолчанию за день до следующего занятия; если график неизвестен — трое суток.
- **Тон** — заголовок конкретный и человеческий («Условные предложения и лексика 28 июля»), `rationale` объясняет выбор в двух-трёх предложениях от лица преподавателя.
- **Уведомления** — ровно одно сообщение в Telegram при выдаче задания (с кнопкой `web_app`) и не более одного напоминания за сутки до срока. Отправляет Hermes, не бэкенд.

## Тестирование

**Бэкенд (bun test, по образцу `cards/router.test.ts`):**

- валидация создания: границы 3/30 карточек, длины полей, `due_at` в прошлом и дальше 30 дней, неизвестные и неактивные `card_id`, дубли;
- единственность активного задания: второе создание → 409; с `replace: true` → предыдущее `expired`;
- ленивое истечение: чтение после `due_at` меняет статус, повторное чтение идемпотентно;
- зачёт: Good и Easy проставляют `completed_at`, Again и Hard — нет; повторный Good не перезаписывает `completed_at`;
- завершение: закрытие последнего элемента переводит задание в `completed` и ставит `completed_at`;
- `drill: true` не пишет в `cards` и `card_reviews`, но двигает прогресс задания;
- `drill: false` пишет и то, и другое (регресс существующего поведения);
- диагностика: пороги пиявок, сортировки, лимиты, корректный `last_assignment` для трёх статусов.

**Фронтенд (bun test, по образцу `practiceHelpers.test.ts`):**

- построение очереди из задания: порядок по `position`, исключение выполненных, возврат карточки после Again **и после Hard** (ни то, ни другое не проставляет `completed_at`, поэтому карточка, ушедшая из очереди на Hard, остаётся должной и недостижимой до следующего захода);
- выбор флага `drill` — первый ответ за день без него, последующие с ним;
- расчёт прогресса и группировки для главного экрана.

## Что осознанно не делаем

- **Упражнений и письменных заданий с проверкой** — только карточки. Проверка свободного текста — отдельная большая фича, у неё своя цена и свои режимы отказа.
- **Ручного создания заданий пользователем** — противоречит смыслу: задание работает потому, что его задал кто-то другой.
- **Нескольких активных заданий** — это возвращает накопительный долг, от которого фича и уходит.
- **Отложенного расписания FSRS для карточек задания** — сложность фильтрованных колод Anki не оправдана.
- **Частичного зачёта по времени просмотра** вместо оценки — «посмотрел» не равно «выучил».
- **Напоминаний со стороны приложения** — единственный канал давления это Telegram-сообщение от Hermes.

## Дополнение 2026-11-03: повторы («Круги»)

Первая итерация сделала задание одноразовым: закрыл — карточки ушли по FSRS в будущее, задание исчезло с главной. Для владельца это оказалось главной претензией — «прогнал один раз, но на 100% не запомнил, а снова прогнать не могу». Повторяемая тренировка добавлена как отдельный режим поверх задания.

- **Сданное задание остаётся на главной до `due_at`.** Вместо кольца due Home показывает `✅ Сдано` и CTA «Повторить задание»; после дедлайна оно живёт только в истории. `GET /assignments/latest` отдаёт последнее задание любого статуса (Home скрывает его, если дедлайн прошёл).
- **Повтор — это drill-сессия по всем карточкам задания**, независимо от `completed_at` и FSRS due. `GET /assignments/:id` отдаёт задание с карточками; очередь строится `buildDrillQueue` (в отличие от `buildAssignmentQueue`, которая для обычной сессии фильтрует незакрытые).
- **Круги не ограничены.** После каждого — экран «Круг N · X из Y» с кнопками «Ещё круг» и «Закончить». Again не возвращается в текущий круг (карточка появится в следующем), Hard возвращается в текущий — как и в обычной сессии задания.
- **FSRS остаётся однозначным.** Первый ответ по карточке за локальный день — измерение, повторы в тот же день — `drill:true`. Круги не меняют статус задания; Good/Easy в круге по всё ещё активному заданию по-прежнему закрывают его items (`markCardCompleted` живёт в общем `applyReview`).
- **Три точки входа:** Summary после сессии задания («Ещё круг»), карточка сданного задания на Home, история (тап по строке раскрывает `rationale` и состав, оттуда «Повторить»).
- **Что не меняется:** одно активное задание, автоматическое завершение, отсутствие напоминаний, свободная практика как отдельный клапан. Hermes не должен пересоздавать задание для повтора — это делает приложение.
